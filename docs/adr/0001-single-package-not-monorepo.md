# ADR 0001 · 单包而非 monorepo（不引入 TurboRepo）

- **状态**：已采纳
- **日期**：2026-10-30

## 背景

`dsh-axzo-theme`、`dsh-usage-query`、`dsh-plugin-expander` 三个插件要合并进 `dsh-usage-aggregator`。需求是**一个插件**（不是把每个功能拆成独立插件），因为「每新增一个插件，设置面板就会多一个入口」。

同时存在一个需要评估的选项：是否采用 TurboRepo 这类 monorepo 方案。

## 决策

**单包 + 目录式模块架构。不用 TurboRepo，也不用 pnpm workspace。**

## 理由

1. **插件管理器按包列条目。** 需求本身就是「一个插件」，多包 = 多行 = 正是要消除的问题。TurboRepo 的最小单位是 package，用它装一个 package 自相矛盾。
2. **产物必须是一个文件。** DSH 的客户端加载器按包名注册**一个**模块（`window.__ModuleLoader__.load({id, factory})`），`exports["./client"]` 也只指向一个 `client/client.js`。三个功能必须融进同一个 bundle。多包要么各自出 bundle（DSH 只加载本包那个，其余白做），要么再加一层组装包 —— 凭空多一个构建层。
3. **Turbo 的价值用不上。** 任务图、构建缓存、远程缓存都是为「多个独立包并行构建」服务的。本仓库只有一个可发布产物、一条构建命令。
4. **包边界解决不了真正的耦合。** 真正的问题是作用域污染（拼接式共享 factory 作用域里 `h` / `NS` / `STYLE_ID` / `zh` / `Panel` 全撞名）。这靠模块作用域解决，不靠包边界；包边界反而带来「改一个功能要发两个版本」的成本。
5. **子目录 + 显式契约的隔离度足够**，而且不需要每个子目录一份 package.json / version / build 配置。
6. **同一用户的既有生态也是这个答案**：`axzo-dsh-plugins` 就是 pnpm workspace（无 Turbo）+ 自建构建脚本。

## 后果

- **正面**：插件管理器一行、设置面板一个入口、一条构建链、一个验证入口；新增功能只加一个目录 + 两行登记。
- **负面**：所有功能共享一个版本号 —— 只想发一个功能的修复时，要跟其它功能一起发。这与「一个插件」的需求一致，是**被接受的代价**。
- **代价可控**：将来若要按功能独立发版，改成「内部 workspace 包 + 一个聚合壳」的形状即可，插件管理器里依然只有一行。详见 ARCHITECTURE.md §3.3。

## 复审触发条件

出现以下任一情况时重新评估：

- 功能数超过 ~8 个，且开始出现合并冲突；
- 出现「只想发某一个功能」的明确需求；
- 需要多个功能由不同团队并行开发。
